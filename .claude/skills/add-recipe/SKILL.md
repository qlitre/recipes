# レシピページを追加する

## 前提

リポジトリルート（`app/routes/recipes/` と `tools/` がある階層）で作業する。コマンドはすべてルートからの相対パスで書いてある。

1レシピは3点セットで成立する。どれか欠けると壊れたページになる。

| もの | 場所 |
|------|------|
| 本文 | `app/routes/recipes/{slug}/index.mdx` |
| 画像 | `public/recipes/{slug}/hero.png, step1.png …` |
| 元画像 | `originals/`（gitignore 対象。リサイズ前の置き場） |

`/recipes/{slug}` というURLとトップページのカードは、この2つのディレクトリ名と frontmatter から自動で決まる。一覧への手動登録は不要。

## 流れ

情報を集める → 雛形生成 → 写真の割り当て → frontmatter → 本文 → 検証。
写真が手元に無い、または手順の詳細が曖昧なまま進めると後で全部書き直しになるので、Step 1 を飛ばさない。

## Step 1. 情報を集める

ユーザーから最低限これを引き出す。足りなければ聞く。

- **slug**: URL とディレクトリ名になる英小文字ハイフン区切り（`low-temp-char-siu`, `onsen-tamago`）。料理名のローマ字か英語。ユーザーが指定しなければ料理名から案を出して確認を取る。
- **料理の内容**: 材料と分量、調理手順、温度と時間、器具。
- **写真**: `originals/` に入っているか、他の場所にあるか。無ければ画像なしで書いて後から足す。

**温度・時間・分量は絶対に推測で埋めない。** このサイトのレシピは低温調理が多く、「63℃で2時間」のような数値は食中毒リスクに直結する。それらしい数字を補完すると、読んだ人が危険な加熱条件で作ってしまう。ユーザーが言っていない数値は空欄にして「ここは何℃で何分でしたか」と聞く。同じ理由で、既存レシピの `## 注意点` には安全側の但し書き（表面を焼く、など）が入っている。低温調理のレシピなら同様の注意書きを入れるか確認する。

## Step 2. 雛形を作る

```bash
./tools/create_recipe.sh slug=your-slug            # date 省略で今日
./tools/create_recipe.sh slug=your-slug date=2026-03-22   # 作った日を指定したいとき
```

`app/routes/recipes/{slug}/index.mdx`（frontmatter 入りテンプレート）と `public/recipes/{slug}/` の**0バイトの** `hero.png` / `step1-3.png` ができる。

ディレクトリが既にあると失敗する。作り直したいときは中身を確認してから消す。

## Step 3. 写真を工程に割り当てる

`resize.sh` は `originals/` から **basename が一致するファイルをコピーするだけ**なので、先に `originals/` 側でリネームしておく必要がある。

1. **写真の置き場所を突き止める。** ユーザーは「写真はルートに置いた」のようにリポジトリ直下へ放り込むことがあり、`originals/` に入っているとは限らない。`git status --short` で未追跡の `IMG_*.png` を探すのが速い。`resize.sh` は `originals/` しか見ないので、別の場所にあるなら次のリネームと同時に `originals/` へ移す。
2. `ls originals/` で中身を把握する。iPhone からだと `IMG_2491.png` のような連番で入っている。ファイル名の連番は撮影順の手がかりになるが、更新時刻（`ls -tr`）は転送時に崩れていて当てにならないことが多い。
3. **必ず全部の画像を開いて中身を見る**（Read tool）。連番＝工程順とは限らず、失敗写真や別料理の写真、前回の残りが混ざっていることもある。何が写っているかを確認してから順番を決める。ここを飛ばすと、手順と関係ない写真が並んだページができあがる。
4. **前回のレシピの元画像を退避する。** `originals/` には前回の `hero.png` / `step*.png` が残っている。ユーザーはこれらを消さず取っておく方針なので、上書きせずサブディレクトリへ move してから今回の写真を置く。

```bash
mkdir -p originals/_前回のslug && mv originals/hero.png originals/step*.png originals/_前回のslug/
```

5. 完成写真を `hero.png`、工程写真を調理順に `step1.png`, `step2.png` … へリネームする（別の場所にあった写真はここで `originals/` へ移す）。工程写真は3枚に限らず増やしてよい（`ratatouille` は12枚）。
6. リサイズして配置する。**使うファイルを明示的に列挙する**:

```bash
./tools/resize.sh your-slug hero.png step1.png step2.png step3.png
```

引数を省くと `originals/*.png` すべてが対象になる。退避し忘れた前回分や、過去の撮影の `IMG_*.png` まで巻き込んで `public/` に撒いてしまうので、必ず列挙する。

`sips -Z 800` で長辺800pxに縮小される。**`jpegtran` が `Not a JPEG file: starts with 0x89 0x50` と出るのは PNG では正常**で、ファイルは無傷のまま次へ進む。このエラーの調査に時間を使わない（JPEG のときだけ最適化が効く）。

7. **使わなかった0バイトのプレースホルダを消す。** `create_recipe.sh` が作る空 png は、そのまま残すと壊れた画像アイコンとして表示される。

```bash
find public/recipes/your-slug -size 0 -delete
```

## Step 4. frontmatter を書く

`app/types.ts` の `Meta` 型がスキーマ。必須は `title` / `slug` / `date` / `image`。

```yaml
---
title: 低温調理チャーシュー
slug: low-temp-char-siu
date: 2025-05-18
description: "60℃・2時間の低温調理で桜色のしっとりチャーシューに。八角とマーガオ香る本格的な中華だれが決め手。"
image: /recipes/low-temp-char-siu/hero.png
servings: 3-4人分
prep_time: 30m
cook_time: "2h"
tags: [中華, 豚肉, 低温調理]
---
```

- **`slug` はディレクトリ名と完全一致させる。** `recipes/_renderer.tsx` がこの値から OGP URL と X シェア URL を組み立てるので、ズレると共有リンクが404になる。
- `description` は120字以内。OGP とトップページのカードに出る要約で、味や決め手が伝わる一文にする。省略すると分量・時間・タグから機械的な文字列が自動生成されるだけなので、基本は書く。
- `date` は `YYYY-MM-DD`。
- **写真が用意できないときは `image` の行ごと削る。** 存在しないファイルを指すとカードとOGPが壊れた画像になる。行が無ければヒーロー画像の描画自体がスキップされて普通に読めるページになる（OGPは `/static/default-og.png` にフォールバックするが、このファイルは現状リポジトリに無いのでOGP画像は出ない）。写真は後から足せるので、それまでは空欄でよい。
- `tags` はインライン配列。既存の語彙（`低温調理` `シャトルシェフ` `中華` `豚肉` `野菜料理` など）を優先して使うと一覧の分類が揃う。器具名をタグにするのはこのサイトの慣習。
- `servings` / `prep_time` / `cook_time` は表記ゆれがある（`30m` と `30分` が混在）。新規は `30m` / `2h` 形式で揃える。

## Step 5. 本文を書く

既存レシピの構成に合わせる。見出しレベルを変えるとスタイルが崩れる。

```markdown
## 材料
- 豚バラブロック … 400g

### たれ原料          ← 調味料やたれがあるときだけ
- 醤油 … 300 mL

### 資材              ← 器具。低温調理器やシャトルシェフなど
- 低温調理器

## 作り方

### 1. **下準備**
- 手順を1行1アクションで書く
![たれを煮立たせている鍋](/recipes/your-slug/step1.png)
- 次の手順

### 2. **調理**
...

### 3. **仕上げ**
...

## 注意点          ← 安全上の但し書き、失敗しやすい点
- ...
```

末尾には必要に応じて `## 食べ方のおすすめ` や `## 参考動画`（参考にした動画のリンク）を足してよい。

書き方のポイント:

- **画像は対応する手順行の直後に置く。** 読む人は手順と写真を交互に見る。まとめて末尾に置かない。
- **alt テキストには何が写っているかを書く。** `![工程画像](...)` では画像が読み込めなかったときもスクリーンリーダーでも情報がゼロになる。`![低温調理機用コンテナにセットした様子](...)` のように具体的に書く。写真を見て書くこと。
- 手順は体言止め・常体で短く（「空気を抜く」「57℃、3.5hで低温調理する」）。長い説明文にしない。
- 分量の区切りは `…` か `...` を使う。既存は混在しているので1ファイル内で揃っていればよい。
- ユーザーのメモにない工程を創作しない。写真から推測できる範囲を超えたら聞く。

書き終えたら、温度・時間・分量など**事実に関わる部分を箇条書きで提示して確認を取る**。文章表現はこちらで決めてよいが、数値の裏取りはユーザーにしかできない。

## Step 6. 検証する

```bash
python3 .claude/skills/add-recipe/scripts/check_recipe.py your-slug
```

frontmatter の必須キー、slug とディレクトリ名の一致、画像参照のリンク切れ、0バイトのまま残ったプレースホルダ、リサイズ忘れ（800px超）、汎用的すぎる alt をまとめて検出する。ビルドはこれらでは落ちないので、目視だけに頼らない。ERROR が出たら直してから次へ。

```bash
yarn build
```

`dist/recipes/{slug}.html` が生成されれば成功。生成物を軽く確認する（タイトル、OGP の画像URL、画像パス）。

ここまででスキルの仕事は完了。`git commit` と `yarn deploy` はユーザーが判断するので、勝手に実行せず「build が通った、commit と deploy はどうするか」と報告する。

## つまずきやすい点

- `resize.sh` は出力先ディレクトリが既存であることが前提。`create_recipe.sh` より先に実行すると `Output directory ... does not exist` で止まる。
- `sips` と `jpegtran` は macOS 前提（`jpegtran` は Homebrew）。別環境では手動リサイズして `public/recipes/{slug}/` に直接置く。
- `originals/` と `dist/` は gitignore されている。コミット対象は `app/routes/recipes/{slug}/index.mdx` と `public/recipes/{slug}/*.png`。画像を add し忘れると本番だけ画像が出ない。
- frontmatter に `Meta` 型に無いキーを足しても表示されない。項目を増やすなら `app/types.ts` と `recipes/_renderer.tsx` の両方を直す必要がある。
